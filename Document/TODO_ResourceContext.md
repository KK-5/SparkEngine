# 资源上下文：资产的身份、引用与淘汰

> 记录「把资产做成一个 ECS 上下文」这个方向的动机、形态、边界与拦路点。
> **优先级：方向探索，未定案。不阻塞任何在建工作**（阶段 3 材质资产、阶段 2、阶段 4）。
>
> **边界（重要）：本文只谈 CPU 侧资产的身份与生命周期。**
> GPU 驻留是另一条轴，归 `TODO_ResourceResidencyPipeline.md`；那份 §3.1 已**否决**
> 「用资产引用计数做驻留判据」，§1 已定「去重 pool 不可省」。本文不碰、也不修正那条线。

---

## 1. 问题：引用没有统一形态，所以枚举不出来

今天一个资产引用可能长成这些样子：

| 持有者 | 形态 | 例子 |
|---|---|---|
| 世界组件 | `AssetId` + `Ptr` 两份 | `MeshComponent{ m_modelAssetId, m_modelAsset }` |
| 另一个上下文的组件 | `AssetId` + `Ptr`，嵌在数组里 | `MaterialParams::m_textures[i]` |
| **资产数据自己** | `AssetId` 数组 | `ModelAssetData::m_imageAssetIds`、材质的贴图 id |
| 编辑器代码 | 临时构造的 `AssetId` | Browser 的图标 |

三种持有者、两种表示，还有一类根本不在任何 ECS 里（资产引用资产）。

于是**「场景还需要哪些资源」这个问题今天问不出来**——没有一个地方能把引用列全。这才是「资产与场景的映射关系乱」的准确描述，而不是「缺少释放机制」。

`AssetDataBase` 持强 `Ptr<Asset>`、永不释放（欠账表里那条），掩盖了这件事：因为什么都不释放，所以从来不需要回答这个问题。

---

## 2. 方向：资产是一个上下文里的实体

一个实体 = 一份资源，状态全是它的组件：

| 组件 | 今天在哪 |
|---|---|
| `AssetRef { AssetId }` | `AssetDataBase` 的 map 键 |
| `AssetStatus` | `Asset` 的成员 |
| `Ptr<AssetData>` | `Asset` 的成员 |
| 上次使用帧 / 优先级 / 驻留等级 | **不存在** |

先例在仓库里：`RHIContext = BasicContext<RHIHandle>` 已经对 RHI 资源做了同一件事——资源、view、pass attachment 都是那个上下文里的实体，`TransientTag` / `ImportedTag` / `ResourceName` 是它们的组件。这个方向是「对资产做同样的事」。

### 2.1 一个必须接受的结构后果

**它取代 `AssetDataBase`，不是与之并列。**

`AssetDataBase` 就是 `AssetId → Ptr<Asset>`，资源实体持有同一份映射。两个都留着就要同步两个索引。所以这条路一旦走，`AssetDataBase` 降级成查找加速结构（`AssetId → ResourceHandle`），`Asset` 对象本身要拆——它今天的成员（id / status / data）正好就是那几个组件。

---

## 3. 收紧一条：authored 引用仍然是 `AssetId`

世界组件**不能只存 handle**，会撞两堵墙：

1. **淘汰之后回不来。** 资源淘汰 = 实体销毁 = handle 失效。entt 的版本号让它可**检测**（比裸指针悬挂强），但检测到之后世界不知道该重新加载什么——handle 里没有 `AssetId`。
2. **场景文件存不了。** 场景要记「我引用 `project://Wood.smat`」，不是「实体 47」。

所以形态是：

```
authored（可序列化、可枚举、可失效重建） = AssetId
解析缓存（运行期、可丢弃、不参与所有权）  = ResourceHandle
```

这正是 `MeshComponent{ m_modelAssetId, m_modelAsset }` 今天的形状，只是把 `Ptr` 换成 handle。

**这条同时说明了「资源上下文」的真正价值**：它不是把引用换一种写法，而是给**解析结果和资源状态**提供一个统一的家。一张 `unordered_map` 只能装解析结果，一个上下文能装状态、并让策略变成系统。

---

## 4. 它买到什么 / 不买什么

**买到：**

- **枚举免费**——遍历上下文即可，不必再去各处找引用者
- **状态数据化**——「上次使用帧」「优先级」这类今天不存在的东西有地方放
- **淘汰策略变成一个系统**——`GetView<AssetRef, LastUsedFrame>` 上跑一遍，与渲染那些系统同构，策略可换
- **散落的解析表收敛**——阶段 3 那张 `AssetId → MaterialHandle` 表可以变成资源实体上的一个组件

**不买：生命周期判定。**

**ECS 上下文本身没有所有权语义。** 「这个资源还有没有人要」在上下文里仍然只能靠下一节那两条路之一回答。把资源装进上下文**不会**消掉这个问题，只会给它一个更好的工作台。

---

## 5. 生命周期：与两份已有文档的关系（本文最需要定案的地方）

两条路，各自都在已有文档里被讨论过，且结论不一致。

### 5.1 引用计数（`Ref<H>`）

`TODO_HandleLifetimePlan.md` §5 选定的方向：计数挂在被引用实体上，引用方持 `Ref<H>`，构造 incref / 析构 decref，由 entt 的组件寿命自动驱动。

**资产引用正好满足那份文档 §3.3 的判据**——多对一共享（多个组件引用同一贴图、同一模型），而共享正是「引用方负责释放」崩溃的地方。

但 `TODO_ResourceResidencyPipeline.md` §6 随后把 `Ref<H>` **降级为「可选优化，暂不做」**，理由是纹理那条线的 liveness 根在渲染需求、现状 scan-GC 已经精确。那条修正针对的是**驻留轴**；资产身份轴不在它的射程内，所以 `Ref<H>` 对本文这条线**仍然是候选**，不是已否决。

**已知弱点：原地改字段不触发任何信号。** `m_textures[i] = 另一个 id` 这类写法会漏掉 incref/decref。仓库那条「反射写组件一律 `set()` + `ReplaceComponent`，不原地改」的约定挡住大部分，但挡不住非反射路径。

### 5.2 可达性遍历

从所有上下文的 `AssetRef` 字段出发走一遍，加上资产之间的边。

**这条基本等同于 `TODO_HandleLifetimePlan.md` §5 的方案 C，而那份已经否决它**，理由是「保留了扫描，正是要消灭的东西」。

但资产有一个句柄没有的情况，需要重新审这个否决：

> **一个还没解析的 `AssetId` 持不了引用。**
> 编辑器必须允许「引用了一个还没加载、甚至暂时找不到的资产」——那个引用真实存在、要参与可达性、要被序列化，但它没有对象可指，因此不可能被引用计数覆盖。

所以对资产而言，引用计数只能覆盖**已解析**的那部分，权威答案仍要来自 `AssetId` 那一侧。

### 5.3 因此的倾向（未定案）

**两者都要，分工明确**：`Ref<H>` 当快路径（热资源不等遍历就活着，且消灭稳态扫描），遍历当权威（切场景、显式「清理未使用资源」、打包可达性分析时按需跑，**不是每帧**）。

与被否决的方案 C 的差别在于：C 是**用扫描替代计数**，这里是**用扫描覆盖计数够不着的那一块**，且频率从每帧降到按需。

**这一条需要和 `TODO_HandleLifetimePlan.md` 的作者视角对一次**，否则等于绕开一个已有结论。

## 6. 边界：不碰 GPU 驻留

`TODO_ResourceResidencyPipeline.md` §3 定了两条独立的轴，本文只在第一条上：

| 轴 | 由什么驱动 | 归谁 |
|---|---|---|
| **身份 / 去重** | 资产（内容 key） | **本文** |
| **驻留 liveness** | 渲染需求（组件引用 / 可见性） | `TODO_ResourceResidencyPipeline.md` |

三条不能碰的既有结论：

- **去重 pool 不可省**（§1），它是上层 feature producer 的状态
- **资产引用计数不能当驻留判据**（§3.1）——资产计数包含资产浏览器、缩略图这些与渲染无关的持有者，拿它决定 VRAM 会过度保留
- **`MaterialTextureSystem` 的两条轴摆对了，核心模型不用换**（§3.2）

> 讨论中曾出现「资源上下文一来，`MaterialTextureSystem::m_pool` 就消失」的说法，**那是错的**，与上面三条冲突。pool 属驻留轴，最多换个家，不因资产侧的改动而消失。

---

## 7. 两个拦路点

**1. 线程模型（最硬的一条）。** 今天 `ProcessAsset` 跑在 worker 线程，靠 `shared_mutex` 保护 map 就够了。**entt registry 不是线程安全的，也不接受并发建实体。**

要么 worker 只产数据、由主线程提交进上下文（资产变 Ready 的时机从「worker 随时」变成「主线程某个 tick」），要么给上下文加锁（等于放弃 ECS 的性能优势）。前者更对，但它改变资产可见的时机，现有测试里有依赖 `OnAssetReady` 时序的用例。

**2. 序列化形态。** 世界组件里那个字段 authored 是 `AssetId`、运行期是 `ResourceHandle`，读写时要互转（写时 handle → id，读时 id → intern 成 handle）。这需要一个声明式的字段标记，与阶段 4 给 `MaterialHandle` 设计的 `EntityRef` 重映射是同一类机制、可共用。

---

## 8. 与阶段 3（材质资产）的关系：顺向，不需要预留

阶段 3 已定的三件事正好是这套的前置形态：

- 材质对贴图的引用是 `AssetId`（`Ptr` 已决定移出组件，并进解析表）
- 材质对资产的引用是 `MaterialSource{ AssetId }`，一个标准的引用字段
- 材质实例由一张按 `AssetId` 索引的表持有

将来上这套时，材质那边改的是「表长什么样」，不是「引用怎么表达」。**阶段 3 不需要为本文预留任何东西。**

另外澄清两个同名的 GC，它们分属两条轴、结论不同：

| | 归属 | 结论 |
|---|---|---|
| `MaterialSystem::CollectGarbage`（材质实体） | 身份轴 | 阶段 3 已由「每个实例有明确所有者」消掉 |
| `MaterialTextureSystem::CollectGarbage`（GPU 贴图） | 驻留轴 | 保留，`ResourceResidencyPipeline` §3.2 说它是对的 |

## 9. 第一步的候选（都不动生命周期）

按代价从低到高：

1. **统一引用的形态**——把散落的 `AssetId` + `Ptr` 双持有收敛成「`AssetId` 是引用、解析结果放表」。阶段 3 已经在材质贴图上做了一次，`MeshComponent` 是下一个。纯重构，行为不变。
2. **引用字段的反射标记**——给引用字段打一个标记，使「遍历所有上下文收集资产引用」成为可能。它与阶段 2 的反射遍历是同一次遍历，做完就能回答「谁引用了这个资产」，编辑器立刻受益，且不动任何生命周期。
3. **资产之间的边**——即 `TODO_AssetSystemPlan.md` 的**待办 A**（通用依赖机制），同时解锁 shader / `.gltf` 缓存。
4. **资源上下文本体**——门槛是 §7 的线程模型。
5. **淘汰**——前四步的自然结果，那时 `AssetDataBase` 松手才有意义。

第 1、2 步可以独立做、独立验证，且不预设本文其余部分是否成立。

## 10. 待定

- §5.3 那条分工（`Ref<H>` 快路径 + 按需遍历权威）与 `TODO_HandleLifetimePlan.md` §5 对方案 C 的否决之间，要不要正式修正那份文档。
- `ResourceHandle` 的形态：`BasicContext<ResourceHandle>` 还是复用 `Entity`。
- 资源实体与 `Asset` 对象的关系：`Asset` 拆成组件，还是保留 `Asset` 对象、实体只持 `Ptr<Asset>`（后者改动小得多，但状态就仍在对象里，买不到 §4 的「状态数据化」）。
- 抖动：refcount 归零就卸载、下一帧又被引用就重新加载。需要一层有界的 LRU 缓冲，形态未定。
- `Object` 的 intrusive 计数是否原子——资产在 worker 线程构建、可能在任意线程被最后一个引用释放。
